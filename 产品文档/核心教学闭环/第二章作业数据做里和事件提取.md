第二章 作业数据处理和事件提取

1. 产品目标

本模块负责记录和处理学生从首次提交作业、AI 初步分析、必要时的诊断追问、AI 初步批改、老师审核并发送批改，到学生完成订正的完整业务流程，并从中提取标准化作业事件。

最终输出的作业事件进入统一 Event Pool，作为后续 Context 生成模块的输入。

本模块主要回答：

学生首次独立完成作业时实际表现如何；
学生答案和解题过程中有哪些正确部分、错误部分或关键遗漏；
当现有作答数据不足以判断学生具体困难时，是否需要通过 Diagnostic Probe 补充证据；
Diagnostic Probe 后，系统能否更可靠地定位当前可观察问题；
AI 能否可靠完成批改，哪些批改需要老师确认或手动完成；
系统最终向学生发送了什么批改和订正任务；
学生收到批改后是否提交订正，订正前后发生了什么可观察变化；
同一份作业中是否出现具有教学价值的重复表现；
每条作业事件来自哪些作业记录。

↓

本模块只处理作业场景数据。

当前包含：

作业及其中的题目；
学生首次提交的答案和解题过程；
学生作答的原始图片、笔迹或结构化输入；
AI / 数学引擎对学生答案的分析结果；
Diagnostic Hypothesis；
Diagnostic Probe；
学生 Diagnostic Response；
AI 生成的初步批改；
老师确认、修改或手动完成的最终批改；
最终实际发送给学生的批改版本；
可选的学生订正任务；
学生收到批改后的订正提交；
作业处理过程中的状态和版本；
最终作业事件。

其中：

学生首次提交不得被后续 Diagnostic Response 或订正覆盖；
AI 作答分析属于中间分析结果，不等于正式作业事件；
Diagnostic Hypothesis 属于中间诊断假设，不等于正式作业事件；
Diagnostic Probe 本身属于系统行为，不是学生表现事件；
学生对 Diagnostic Probe 的实际回答属于可观察业务事实，可以作为后续 Homework Event 的来源；
AI 批改草稿不等于学生实际收到的批改；
涉及反馈的作业事件必须以学生实际收到的最终版本为准；
学生查看批改、打开订正页面等系统操作本身不构成学生表现事件；
最终作业事件需要保留事件来源 sourceRefs。3. 数据处理层级

作业数据分为三个主要层级：

作业业务记录
↓
作答 / 诊断 / 批改分析数据
↓
作业事件
3.1 作业业务记录

作业业务记录用于保存真实发生的作业流程。

包括：

作业；
作业中的题目；
某名学生的本次作业；
某名学生本次作业中的某一道题；
学生首次提交；
Diagnostic Probe；
Diagnostic Response；
学生订正提交；
AI 初步批改；
老师最终批改；
Student Task；
作业状态；
最终批改发送记录。

这些记录属于底层业务事实。

3.2 作答、诊断和批改分析数据

AI 或数学引擎可以基于学生提交及 Diagnostic Response 产生中间分析结果，例如：

answerStatus；
正确步骤；
错误步骤；
首个关键错误候选；
可观察问题；
Diagnostic Hypothesis；
跨题重复模式候选；
订正前后变化；
分析置信度；
是否需要继续诊断；
是否需要老师确认。

这些分析用于：

生成 Diagnostic Probe；
更新 Diagnostic Hypothesis；
生成初步批改；
判断批改处理类型；
帮助老师审核；
判断是否形成正式作业事件。

分析结果本身不直接等于正式事件。

3.3 作业事件

作业事件是从作业业务记录和分析结果中提取出的、具有教学意义的客观事实。

例如：

学生首次提交时正确建立方程，但展开括号时未将 3 乘到括号内第二项。

学生在第 8、12、15 题中均未确认直角条件便使用勾股定理。

学生首次提交中列式错误；在诊断追问中表示无法判断总价和数量之间应使用何种运算关系。

学生收到相关批改后，在订正中补充了直角条件并重新完成第 12 题。

作业事件可以描述：

学生首次独立作答中的关键表现；
学生在 Diagnostic Probe 中实际表达出的可观察回答；
多道题中重复出现的具体表现；
学生收到最终批改后发生的订正变化。

作业事件不得直接描述：

学生已经掌握某个知识点；
学生长期不会某项能力；
学生粗心；
学生不认真；
学生理解能力差；
某个 Diagnostic Hypothesis 已经被证明为长期事实；
本次批改已经证明有效；
某种教学方式应该保留或调整。

因此：

作业事件
= 可观察的作业表现、回答和变化

作业事件
≠ 长期学习判断
≠ Diagnostic Hypothesis
≠ 批改效果结论
≠ 教学策略判断
≠ Lesson Kit 调整建议 4. 作业采集与提交版本
4.1 平板 / 电子笔作业

系统可以保存：

原题；
正式答案；
草稿；
矢量笔迹；
笔迹顺序；
擦除和撤销；
多次保存或提交；
已发生的 AI 或老师支持记录；
正式提交时间。

只有真实采集到的数据才能用于学生作答过程分析。

4.2 结构化在线作答

对于选择题、填空题、结构化数学输入等，可以直接保存：

questionId；
学生答案；
输入过程；
提交版本；
提交时间；
客观判分结果。
4.3 纸质拍照作业

系统可以处理：

页面校正；
题目匹配；
解答区域切分；
手写文字识别；
数学公式识别；
图形识别；
最终答案提取；
主要步骤提取；
首次提交与订正版本匹配。

纸质拍照通常无法可靠恢复：

真实书写顺序；
停顿；
擦除过程；
学生是否使用外部帮助。

不得根据不存在的数据强行推断这些行为。

4.4 Submission 版本原则

学生每次正式提交都保存为独立 Submission。

当前至少支持：

initial
correction

业务关系为：

Initial Submission
↓
必要时 Diagnostic Probe
↓
老师发送最终批改
↓
Correction Submission

Diagnostic Response 不属于 Submission。

首次提交不得被 Diagnostic Response 或订正版本覆盖。

当前版本不包含：

首次提交
→ Feedback
→ 再提交
→ 再 Feedback
→ 再提交

这类多轮支持流程。

Diagnostic Probe 属于首次提交后的诊断补充，不属于多轮订正。

6.1 作答分析目标

学生首次提交后，AI / 数学引擎对每道题进行分析。

至少包括：

判断答案状态；
识别主要解题步骤；
判断本题是否要求展示完整过程；
识别已经正确完成的部分；
识别错误、遗漏或无法判断的部分；
在能够可靠判断时定位首个关键错误候选；
识别可用于同一份作业内跨题比较的具体模式候选；
输出分析置信度；
判断当前证据是否足以描述关键问题；
证据不足时生成 Diagnostic Hypothesis；
判断是否需要 Diagnostic Probe。

答案状态至少包括：

correct
partially_correct
incorrect
unanswered
unable_to_judge

6.3 诊断证据充分性判断

完成首次 AI Analysis 后，系统判断：

当前已有作答数据是否足以支持后续批改和教学分析。

输入可以包括：

最终答案；
解题步骤；
正确 / 错误步骤；
首个关键错误候选；
尝试次数；
Hint 使用；
作答时间；
同一份作业内相关题目表现；
近期相关 Homework Event。

输出至少包括：

sufficient
insufficient
sufficient

表示现有证据已经足以描述当前可观察问题。

例如：

学生正确建立方程，但展开括号时未将 3 乘到第二项。

此时不需要额外追问。

insufficient

表示当前错误存在多个合理解释，已有数据不足以判断关键问题。

例如：

学生最终列式错误，但无法判断是没有识别数量关系，还是在设未知量时已经出现偏差。

此时可以进入 Diagnostic Probe。

6.4 Diagnostic Hypothesis

当诊断证据不足时，系统可以生成一个或多个候选 Diagnostic Hypothesis。

Diagnostic Hypothesis 用于表示：

系统当前认为可能存在的若干解释。

例如：

{
"hypothesisId": "hypothesis_001",
"studentAssignmentQuestionId": "saq_001_012",
"analysisRecordId": "analysis_012_v1",
"hypothesisType": "quantity_relationship_issue",
"description": "学生可能未正确识别题目中的数量关系",
"confidence": 0.42
}

第一版可以支持：

reading_comprehension_issue
unknown_variable_issue
quantity_relationship_issue
equation_setup_issue
condition_identification_issue
calculation_issue
insufficient_evidence
other

具体枚举后续可按学科扩展。

Diagnostic Hypothesis：

属于中间分析结果；
可以被 Diagnostic Response 更新；
不等于正式 Homework Event；
不直接写入 Context；
不允许被描述成长期学生能力结论。
6.5 Diagnostic Probe 触发条件

满足以下情况之一时，可以触发 Diagnostic Probe：

当前错误存在多个合理解释；
同类问题重复出现，但关键原因仍无法定位；
当前判断会明显影响后续 Feedback 内容；
当前判断可能明显影响后续 Planning；
当前分析置信度不足以生成可靠 Feedback；
需要区分两个或多个 Diagnostic Hypothesis。

以下情况默认不触发：

明确的简单计算错误；
已有解题步骤足以定位问题；
明显笔误或格式问题；
低价值错误；
当前题已完成 Diagnostic Probe；
学生已经达到本次最多追问次数。

系统不得因为“学生答错”本身自动触发 Diagnostic Probe。

6.6 Diagnostic Probe 定义

Diagnostic Probe 用于：

当已有作答数据不足时，通过最少的额外交互补充诊断证据。

Diagnostic Probe：

不是 AI Tutor 长对话；
不是 Feedback；
不是 Student Task；
不是 Correction；
不用于重新教学整道题；
不直接告诉学生答案。

一次 Probe 默认只问 1 个问题。

单题最多追问 2 次。

6.7 Diagnostic Probe 类型

第一版支持：

self_report_choice

用于快速获得学生主观感受。

例如：

你刚刚最不确定的是哪一步？

读题；
找数量关系；
列方程；
计算；
我不确定。
concept_check

用于验证具体数学概念或关系。

例如：

这道题中，总价和数量之间是什么关系？

用于区分：

数量关系理解问题；
后续列式问题；
计算问题。
short_explanation

用于学生简单解释自己的思路。

例如：

你为什么把这个量设成 x？

只在选择式问题不足以区分候选 Hypothesis 时使用。

6.8 Probe 问题选择原则

系统不应随机生成追问。

应该优先选择：

对当前候选 Diagnostic Hypothesis 具有最高区分价值的问题。

例如当前候选：

unknown_variable_issue
quantity_relationship_issue
equation_setup_issue

系统应选择能够区分“未知量定义”和“数量关系识别”的问题。

不建议生成：

你为什么做错了？

这类泛化问题。

6.10 Diagnostic Response

学生完成追问后，需要保存实际回答。

{
"diagnosticResponseId": "diagnostic_response_001",
"diagnosticProbeId": "probe_001",
"studentAssignmentQuestionId": "saq_001_012",
"responseType": "multiple_choice",
"responseContent": "不知道是乘法还是加法",
"submittedAt": "datetime"
}

Diagnostic Response：

属于真实作业业务记录；
不属于 Submission；
不覆盖 Initial Submission；
可以作为后续 AI Analysis 的输入；
可以作为正式 Homework Event 的 sourceRefs；
不得单独被解释为长期学生能力结论。
6.11 Diagnostic Probe 结束条件

满足任一条件时结束：

当前证据已经足够区分主要 Hypothesis；
已完成 2 次追问；
学生连续回答“不确定”；
学生跳过追问；
继续追问信息价值较低；
当前问题已经需要教师进一步判断。
6.12 Diagnostic Probe 后重新分析

收到 Diagnostic Response 后，系统重新分析当前题目。

推荐保存新的 Analysis Version，而不是覆盖旧版本。

例如：

AI Analysis v1
↓
Diagnostic Probe
↓
Diagnostic Response
↓
AI Analysis v2

新的 Analysis 可以更新：

Diagnostic Hypothesis；
Hypothesis confidence；
firstCriticalErrorCandidate；
observableIssue；
diagnosticEvidenceStatus；
Feedback 生成条件；
是否需要教师确认。

例如：

6.13 教师确认兜底

如果完成最多 2 次 Diagnostic Probe 后仍无法可靠判断，可以标记：

teacher_confirmation_required = true

系统可以向老师展示：

当前已经确认的事实；
当前仍无法区分的候选问题；
学生的 Diagnostic Response；
建议老师进一步询问的问题。

例如：

当前无法区分“数量关系识别问题”和“列式表达问题”。

建议老师下次课确认：

“你做这道题时，为什么先写这个式子？”

系统不得为了避免教师确认而强行选择某个 Diagnostic Hypothesis。

   7.1 Feedback Item

一个 Feedback Item 可以关联：

一道题；
多道出现相同具体问题的题目。

7.2 Feedback Content

Feedback Content 用于告诉学生：

哪个位置需要关注；
当前答案具体存在什么问题；
哪个条件、步骤或依据需要检查；
哪些部分已经正确；
哪些过程仍需要补充。

例如：

使用勾股定理前，需要先确认当前三角形是否为直角三角形。

Feedback 可以对应文字、手写、语音、标记等不同表现形式，但本章不规定具体 UI。

7.3 Student Task

Student Task 用于告诉学生：

收到 Feedback 后，需要完成什么具体订正动作。

Student Task 为可选内容。

当前版本可以支持：

correct_from_step
retry_question
supplement_reasoning
answer_guiding_question

例如：

请标出题目中的直角条件，并重新完成本题。

不是每一个 Feedback Item 都必须包含 Student Task。

7.4 Diagnostic Probe 与 Student Task 区别

二者必须明确区分。

Diagnostic Probe

发生在：

Initial Submission
↓
AI Analysis
↓
Diagnostic Probe

目的：

补充诊断证据。

特点：

发生在正式 Feedback 之前；
默认 1 次，最多 2 次；
不负责教学和订正；
不进入 Correction Submission 流程。
Student Task

发生在：

Feedback Sent
↓
Student Task
↓
Correction Submission

目的：

让学生根据正式 Feedback 完成订正动作。

因此：

Diagnostic Probe
≠ Student Task
7.5 Feedback 与 Student Task 的业务关系

Feedback Content 和可选 Student Task 共同组成一个完整 Feedback Item。

老师处理一个需要确认的 Feedback Item 时，同时决定：

最终 Feedback Content；
是否包含 Student Task；
Student Task 的具体内容。
7.6 Student Task 生成原则

当前版本 Student Task 只服务于本次作业订正。

常见情况包括：

从错误步骤继续订正

当能够明确定位影响后续解答的错误步骤时，可以要求学生从该位置继续订正。

重新完成整题

当解题方向、数学模型、公式或关键起点存在明确问题，局部修改不足以完成当前题目时，可以要求重新完成整题。

补充关键过程

当：

最终答案可能正确；
本题要求展示过程；
当前提交缺少必要步骤、条件或推理依据；

可以要求补充关键过程。

回答关键条件后订正

当学生使用公式、定理或判定方法，但当前解答没有体现必要条件时，可以要求学生先确认条件，再完成订正。

多题存在相同具体问题

当同一学生在多道题中出现相同具体问题时：

不为每道题机械生成相同 Student Task；
可以形成一个关联多道题的 Feedback Item；
可以选择一道或少量代表题要求学生订正。

无法可靠判断时，不强制生成 Student Task。

8. 批改处理决策

每一个需要反馈的 Feedback Item 都具有一个 handlingType。

第一版包括：

auto
teacher_confirmation
manual
8.1 auto

表示 AI 可以可靠完成该 Feedback Item，老师无需逐项确认。

典型情况包括：

明确计算错误；
明确符号错误；
去括号、移项、通分等程序性错误；
漏写单位；
简单步骤缺失；
标准答案唯一且过程明确的基础题。

业务规则：

AI 生成 aiDraft；
系统可以直接形成待发送 finalVersion；
老师在整份作业发送前仍然可以修改或删除；
不需要老师逐项执行确认动作；
不会因为属于 auto 而提前发送给学生。
8.2 teacher_confirmation

表示 AI 已经形成完整 Feedback Item，但该内容需要老师确认后才能进入最终发送版本。

典型情况包括：

同一种问题在多道题中重复出现；
涉及本次作业的重要教学目标；
答案正确但关键过程或依据缺失；
学生使用非标准但可能成立的方法；
AI 准备要求学生重新完成重要题目；
Student Task 是否必要存在一定不确定性；
Diagnostic Probe 后仍存在一定诊断不确定性，但 AI 已经能够形成候选 Feedback。

老师处理后可以：

confirm
或
switch_to_manual
8.3 manual

表示当前 AI 无法可靠完成正式批改，需要老师处理后才能形成 Final Version。

典型情况包括：

手写、公式或图形识别失败；
学生答案与题目区域无法可靠匹配；
关键内容缺失；
AI 无法确认非标准解法是否成立；
几何证明中的关键推理无法可靠验证；
开放题、多解题缺少明确自动评价依据；
题目或参考答案本身可能存在问题；
AI 无法确定答案状态；
完成 Diagnostic Probe 后仍无法确定应给学生什么 Feedback。9. 作业批改工作流

11.3 homework_initial_performance
事件定义

记录学生在收到本次作业 Feedback 之前，Initial Submission 及必要 Diagnostic Response 中具有后续教学价值的关键表现。

它回答：

学生第一次独立完成这道题，以及必要诊断补充中，发生了什么值得继续关注的可观察表现？

不是每道题都生成该 Event。

可以生成的情况

例如：

题目对应本次作业的重要教学目标；
能够识别影响后续解答的关键问题；
Diagnostic Response 补充了重要的可观察信息；
学生部分正确，且正确部分具有教学价值；
学生采用了具有代表性的解题方式；
同一学生在相关题目中的表现存在明显差异；
该表现本身具有足够后续分析价值。

以下情况默认只保存底层结果：

普通单题正确；
单次简单计算错误；
轻微格式问题；
不影响后续分析的单位或书写问题；
无法明确描述问题的低置信度分析。

11.4 homework_repeated_pattern
事件定义

记录同一学生在同一份作业的多道独立题目中，重复出现的相同可观察表现。

表现可以包括：

相同错误；
相同关键遗漏；
相同解题策略；
重复出现的有效方法；
多道题中稳定完成的关键步骤。

它回答：

某个具体表现是否在多道题中重复出现？

生成要求

至少满足：

关联两道独立题目；
每道题都有可回溯的 Initial Submission；
不能仅因为几道题都错误就判断为同一模式；
不能仅因为几道题都正确就判断为同一模式；
必须能够描述相同的具体步骤、条件、策略或行为；
Diagnostic Response 可以辅助判断，但不得单独替代多题实际表现；
该重复表现具有形成正式 Event 的价值。

当前第二章只要求处理：

同一份作业内的重复模式。

第二章不负责跨作业聚合。

11.5 homework_response_to_feedback
事件定义

记录学生收到本次实际发送的 Feedback 后，Initial Submission 与 Correction Submission 之间发生的关键变化。

它回答：

学生收到此次 Feedback 后，原来的目标问题在订正中发生了什么变化？

当前只比较：

Initial Submission
→
Sent Feedback
→
Correction Submission

Diagnostic Probe 发生在 Sent Feedback 之前，不属于 Feedback Response。

生成条件

至少满足：

Feedback 已经实际发送；
学生提交了 Correction Submission；
Initial 和 Correction 可以进行有效比较；
系统能够识别 Feedback 针对的问题是否发生变化；
该变化具有形成正式 Event 的价值。

学生只查看 Feedback 而没有提交 Correction 时，不生成该 Event。

学生未完成订正时：

可以保留 Student Task 状态。

不能生成：

学生仍然不会。

学生成功完成原题订正，只能说明：

学生能够根据本次 Feedback 完成原题订正。

不能直接说明：

学生已经能够在新的题目中独立应用。

11.6 最终作业事件确认规则
普通题目结果不机械转换为 Event

底层可以保存所有题目的：

correct
incorrect
partially_correct

但不因此为每道题都生成正式 Event。

Diagnostic Hypothesis 不直接转换为 Event

例如系统内部存在：

quantity_relationship_issue = 0.78

不能因此直接生成：

学生不理解数量关系。

必须有可观察的 Submission、Diagnostic Response 或其他业务事实支持。

Diagnostic Probe 本身不转换为 Event

系统问了：

“总价和数量之间是什么关系？”

这是系统行为，不是学生表现。

Diagnostic Response 可以作为 Event 来源

学生实际回答：

“我不知道是加还是乘。”

属于可观察业务事实。

可以作为正式 Homework Event 的 sourceRefs。

同一事实不得重复形成多个正式 Event

如果一个具体重复表现已经被完整表达为：

homework_repeated_pattern

不应再机械生成多条表达完全相同事实的 homework_initial_performance。

系统操作不转换为学生表现 Event

以下行为不属于学生表现：

AI 生成 Diagnostic Hypothesis；
AI 生成 Diagnostic Probe；
AI 生成 Feedback；
老师确认 Feedback；
老师编辑 Feedback；
老师发送 Feedback；
学生查看 Feedback。
不建立未经观察支持的长期判断

单次错误不能转换为：

学生不会这个知识点。

单次 Diagnostic Response 也不能转换为：

学生长期存在该能力缺陷。

Correction 成功也不能转换为：

学生已经掌握这个知识点。

低置信度分析不强制生成 Event

当：

手写识别不可靠；
解题步骤无法恢复；
非标准解法无法判断；
首个关键错误无法确定；
Diagnostic Probe 后仍存在较大不确定性；
跨题模式只是弱相似；

可以只保留 Analysis Record，不生成正式 Event。

{

Event Pool 写入 程序 13. 验收标准
本模块只处理作业场景的数据和 Homework Event。
Classroom Event 与 Homework Event 的关联不在本章完成。
Context 不在本章生成。
Lesson Kit Planning 不在本章生成。
每名学生每道作业题必须能够通过唯一 studentAssignmentQuestionId 关联。
Initial Submission、AI Analysis、Diagnostic Probe、Diagnostic Response、Feedback、Student Task、Correction 和 Event 必须能够关联到对应 studentAssignmentQuestionId。
Initial Submission 不得被 Diagnostic Response 或 Correction Submission 覆盖。
每次正式订正必须保存为独立 Submission。
当前 Submission 至少支持 initial 和 correction。
Diagnostic Response 不属于 Submission。
当前版本不包含多轮 Feedback 后的重复订正。
AI Analysis Record 不得直接等同于正式 Homework Event。
Diagnostic Hypothesis 不得直接等同于正式 Homework Event。
AI Analysis 完成后，系统应能够判断当前诊断证据是否充分。
诊断证据不足时允许触发 Diagnostic Probe。
系统不得因为单纯答错自动触发 Diagnostic Probe。
明确的简单计算错误默认不应触发 Diagnostic Probe。
Diagnostic Probe 默认 1 次，单题最多 2 次。
Diagnostic Probe 的问题应服务于区分当前候选 Diagnostic Hypothesis。
Diagnostic Probe 不应发展成开放式长对话。
Diagnostic Probe 本身不是学生表现 Event。
学生实际 Diagnostic Response 必须保存为独立业务记录。
Diagnostic Response 可以作为 Homework Event 的来源。
Diagnostic Response 不得直接被解释为长期学生能力结论。
Diagnostic Probe 完成后，应生成新的 Analysis Version 或其他可追踪的更新分析结果。
后续 Feedback Item 必须使用最新有效 AI Analysis。
完成最多 2 次 Diagnostic Probe 后仍无法可靠判断时，应允许进入教师确认或 manual 处理。
老师应能够查看必要的 Diagnostic Response 和当前仍无法确认的问题。
AI Draft、Final Version 和学生实际收到的版本必须能够区分。
老师修改或删除 AI Draft 后，不得继续把原 AI Draft 作为学生实际收到的 Feedback。
Feedback Content 和可选 Student Task 作为一个完整 Feedback Item 处理。
Student Task 不是每个 Feedback Item 的必填内容。
Diagnostic Probe 与 Student Task 必须区分。
Diagnostic Probe 服务于提交后的诊断补充。
Student Task 服务于正式 Feedback 后的订正。
当前 Student Task 只服务于本次订正，不包含验证和迁移任务。
Feedback Item 的 handlingType 至少支持 auto、teacher_confirmation 和 manual。
同一 StudentAssignment 中允许同时存在三类 Feedback Item。
teacher_confirmation 类型必须经老师处理后才能形成可发送 Final Version。
manual 类型必须经老师完成处理后才能形成可发送 Final Version。
auto 类型不需要老师逐条确认，但老师在发送前仍可以修改或删除。
确认单个 Feedback Item 不等于发送该 Feedback。
只有所有必须完成的 Diagnostic Probe 和人工处理项处理完成后，StudentAssignment 才能进入 ready_to_send。
ready_to_send 不等于已经发送。
批改必须经过独立发送动作后才能进入 feedback_sent。
已实际发送的 Feedback 版本必须被冻结，不能被后续修改覆盖。
Student Task 的 viewed 不得视为任务完成。
Student Task 完成应能够关联实际 Correction Submission。
当前正式 Homework Event 只包含 homework_initial_performance、homework_repeated_pattern 和 homework_response_to_feedback。
当前不新增独立 homework_diagnostic_response Event。
Diagnostic Response 应通过已有 Homework Event 的 sourceRefs 进入证据链。
普通单题结果默认保留在底层数据中，不要求生成正式 Event。
firstCriticalError 只作为 Analysis 或 Event 可选字段，不单独作为正式 Event。
homework_repeated_pattern 必须至少关联两道独立题目。
重复模式不能只依据多个题目的最终正确或错误状态判断。
Diagnostic Response 不得单独替代跨题重复表现证据。
当前第二章只要求识别同一份作业内的重复模式。
homework_response_to_feedback 必须存在实际 Sent Feedback 和 Correction Submission。
Diagnostic Probe 不属于 Sent Feedback。
学生仅查看 Feedback 不得生成 homework_response_to_feedback。
学生未提交 Correction 不得自动生成“问题仍未解决”事件。
原题订正成功不得记录为独立迁移成功。
同一可观察事实不得重复形成多个正式 Homework Event。
低置信度分析允许只保留在 Analysis 层，不生成正式 Event。
单个 Diagnostic Hypothesis 不得直接转换成 Context。
最终 Homework Event 必须包含 eventId、eventSource、eventType 和 observableSummary。
最终 Homework Event 应尽可能包含课程、学生、知识点、能力点和题目关联。
最终 Homework Event 必须尽可能保存 sourceRefs。
sourceRefs 应支持 diagnostic_response。
系统不建立独立 Evidence 数据实体。
最终 Homework Event 必须符合第三章 Event Pool 的统一输入规范。
本模块只负责输出 Homework Event，不负责决定哪些 Event 最终进入 Context。
